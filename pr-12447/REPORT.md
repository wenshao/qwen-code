#### 2. A corrupt or truncated compressed body still gets Express's HTML error page (small, one-line fix)

By default `express.json` inflates gzip, deflate and br. When inflation fails, body-parser wraps the zlib error as `createError(400, error)` with no `type`. It misses the new `charset.unsupported`/`encoding.unsupported` mapping, and Express's default handler answers with a `400 text/html` page (probe rows D6, D11, D12). So the mapping triage described as closing the escape to Express's error page closes it for the 415s only. How much this matters:

- **Limited impact:** the status still classifies as a protocol error, and this can only happen after the token, `no-store` and lease checks.
- **Stack trace:** outside production (with `NODE_ENV` unset, or `test` under vitest), the page includes a stack trace, `node:internal` frames only. The CLI bundle inlines `NODE_ENV=production`, which cuts the page down to "Bad Request".
- **Last HTML body:** it is the only non-JSON body the application itself still sends.

I suggest setting `inflate: false`:

- **Why it's safe:** a 16 KiB private request gains nothing from compression.
- **What it changes:** body-parser then rejects every non-identity `Content-Encoding` as `encoding.unsupported`, which the existing branch already maps to the JSON 400. The limit also becomes a limit on wire bytes. The probe passes 44/44 once D5 (valid gzip) and D10 (gzip bomb) are expected to get 400.
- **Behaviour change:** a valid gzip request goes from 200 to 400, and the gzip bomb from 413 to 400.
- **To keep gzip instead:** map any body-parser error with a 4xx `status` to the JSON 400.

#### 3. Notes (not blocking)

- **Triage finding 1 doesn't hold.** `npm pack --dry-run` in `packages/cli` does list `dist/src/serve/contracts/*.json`. But `packages/cli/package.json` is `"private": true`. The published CLI is the root `dist/` (`run-release-step.sh` → `publish_package 'dist'`), and `prepare-package.js` gives it a `files` allowlist. Root `dist/` contains none of these files, so they don't reach npm.
- **JSON charset.** body-parser accepts any `utf-*` charset. A UTF-16LE-encoded body sent with `charset=utf-16le` gets 200, as does `charset=utf-7`, and only non-`utf-` charsets fail. RFC 8259 §8.1 requires UTF-8 for JSON exchanged between systems. If the wire contract means UTF-8 only, pin it and add a `utf-16le` case.
- **The JDK sends h2c upgrade headers.** A default JDK 21 `HttpClient` sends `Connection: Upgrade, HTTP2-Settings` and `Upgrade: h2c` on every cleartext POST (captured on the wire; see the JDK replay figure). The bare listener here ignores the upgrade and answers over HTTP/1.1. The daemon's HTTP server destroys cleartext requests that carry `Upgrade: h2c` (I reported this in the #12409 verification). So either the future owned listener must not install an `upgrade` handler of that kind, or the Java transport must pin `HTTP_1_1`, as `sdk-java`'s `DaemonClient` already does.
- **The Java test catches 7 of 8 drifts.** Seven of the eight scripted drifts fail `ManagedRuntimeAttestationConformanceTest`: a changed route path, a status/class mismatch, a dropped class, a duplicate id, a token in the response, a renamed request field, and a 32 KiB limit. The one it missed turns `wrong-lease` into a request that succeeds. As the design doc says, only the TS suite actually runs the cases. The `sdk-java.yml` path filters include `packages/cli/src/serve/**`, so editing the fixtures does trigger the Java lane.
